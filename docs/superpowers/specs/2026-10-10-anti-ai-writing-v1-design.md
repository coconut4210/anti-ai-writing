# Anti-AI-Writing Skill 1.0 架构设计

日期：2026-10-10  
状态：设计已确认，等待书面规格审核

## 1. 目标与范围

Anti-AI-Writing 1.0 面向以下任务：用户给出一个核心论点，要求模型据此完成评论、分析、论证或其他以观点发展为中心的独立创作。

1.0 的目标是生成一篇：

- 忠实保留用户核心论点，不通过加强、削弱、扩大范围或偷换维度制造稻草人；
- 关键推论具有可恢复的依据，段落持续推进论证；
- 不引入无关反方、排除项泄漏和防御链；
- 在缺少经验性证据时，不把预期机制写成已经发生的效果；
- 需要用户决定的证据缺口位于完整正文之后，不混入正文。

1.0 正式启用三个模块：

1. AW-01 稻草人保护；
2. AW-02 逻辑断裂控制；
3. AW-03 防御性写作控制。

1.0 不承诺自动事实核查、未经授权的联网调查、覆盖所有 AI 写作问题、为所有题材固定文章结构、完整诊断任意已有文章，或启用 04—10 模块。

## 2. 调用方式

Skill 采用混合触发。

### 2.1 自动触发

同时满足以下条件时自动触发：

- 用户给出核心论点或明确判断；
- 用户要求据此创作、探讨、分析或论证；
- 主要交付物是独立成稿。

### 2.2 显式调用

用户可以通过 `$anti-ai-writing` 显式启用。

### 2.3 用户开关

用户可以通过自然语言：

- 关闭整个 Skill；
- 跳过指定模块；
- 仅启用指定模块。

模块开关只影响本 Skill 的写作流程，不取消平台安全、事实和权限边界。

### 2.4 默认不自动触发

- 只诊断已有文章；
- 单纯查资料或事实核实；
- 翻译、摘要和格式转换；
- 不以核心论点为中心的小说、广告等创作；
- 用户明确关闭 Skill。

## 3. 仓库与 Skill 结构

GitHub 仓库根目录同时作为可安装 Skill 根目录：

```text
anti-ai-writing/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── shared-contract.md
│   ├── module-interface.md
│   └── modules/
│       ├── 01-strawman.md
│       ├── 02-logic-break.md
│       └── 03-defensive-writing.md
├── evals/
│   ├── strawman/
│   ├── logic-break/
│   ├── defensive-writing/
│   └── integration/
├── docs/
│   └── architecture.md
├── README.md
└── LICENSE
```

职责划分：

- `SKILL.md` 是唯一运行入口，包含触发规则、用户开关、阶段流程、模块注册表和输出边界；
- `references/shared-contract.md` 定义共享状态和字段语义；
- `references/module-interface.md` 定义模块接入契约；
- `references/modules/` 保存真正改变生成行为的运行规则；
- `evals/` 保存测试输入、输出、人工判定和已知失败，不在普通调用时加载；
- `docs/architecture.md` 面向维护者说明架构与扩展方式；
- `README.md` 面向 GitHub 用户说明用途、安装、调用和已知限制。

许可证由用户在发布前选择。实施阶段不得擅自创建或选择许可证文本。

现有 `problem-details/01—03` 是开发源材料，不直接作为运行时引用。迁移时：

- 行为规则进入对应模块；
- 测试矩阵和失败记录进入 `evals/`；
- 开发状态与实施建议进入维护文档；
- 删除不会改变模型决策的重复说明。

## 4. 执行架构

### 4.1 阶段

```text
输入解析
  ↓
PREPARE：AW-01 锁定用户核心论点；AW-03 区分正文目标与排除项
  ↓
PLAN：AW-02 建立论证目标、关系和成立边界
  ↓
COMPOSE：AW-02 控制逻辑与推进；AW-03 拦截防御内容
  ↓
AUDIT：AW-01、AW-02、AW-03 分别产生诊断和修复建议
  ↓
REWRITE：主控合并冲突和重叠范围，统一修改正文
  ↓
VALIDATE：AW-01 复验立场；AW-02 复验逻辑；AW-03 复验防御内容
  ↓
RESOLVE：AW-03 在存在证据缺口时形成正文后的待确认项
```

### 4.2 统一重写

模块不得各自连续重写全文。模块只输出诊断与局部修复建议，主控在 `REWRITE` 阶段统一合并后修改一次正文。

统一重写用于避免：

- AW-01 修复立场后被 AW-02 再次改弱；
- AW-02 补足逻辑后被 AW-03 当作防御内容删除；
- AW-03 删除防御链后留下逻辑缺口；
- 多个模块对同一文本范围反复覆盖。

### 4.3 修复后的复验

任何语义修改至少重新运行 AW-01 和 AW-02 的相关检查。AW-03 引起的删除或改写必须复验立场、关键关系和论证推进。

默认最多运行两轮“诊断—修复—复验”。两轮后仍存在会改变文章方向的关键歧义时，只提出一个关键问题；局部证据缺口不阻塞完整成稿，转入 `RESOLVE`。

## 5. 模块职责

| 模块 | 生成前 | 生成中 | 生成后 | 负责的修改 |
|---|---|---|---|---|
| AW-01 稻草人保护 | 提取并锁定核心论点 | 防止扩大、削弱、绝对化和维度偷换 | 复验立场一致性 | 论点范围、条件和归属 |
| AW-02 逻辑断裂控制 | 建立论证目标和关系计划 | 控制关系强度和内容推进 | 审计关系、重复和停滞 | 逻辑连接、依据强度和段落功能 |
| AW-03 防御性写作控制 | 区分目标、排除项、必要反驳和证据边界 | 拦截虚构反方、约束泄漏和防御链 | 审计防御内容、识别证据缺口 | 防御结构、限定方式和待确认项 |

## 6. 共享状态契约

```yaml
request:
  core_thesis: 用户要求发展的核心论点
  task_type: 评论、分析、论证或其他观点创作
  audience: 目标读者
  length_and_style: 篇幅与表达要求
  explicit_constraints: 用户明确要求
  source_policy: 仅用现有材料或允许调查

runtime:
  enabled_modules: [AW-01, AW-02, AW-03]
  disabled_modules: []
  current_stage: prepare
  revision_round: 0

content:
  intent_spec: 用户立场、内容目标、排除项和证据边界
  argument_plan: 论证目标、关键关系和成立条件
  draft_versions: 草稿与修订版本
  diagnostics: 各模块诊断
  patch_proposals: 待合并的局部修改
  uncertainty_items: 待用户决定的证据缺口
  validation_results: 修订后的复验结果
```

共享状态只用于内部处理。内部字段名、模块标签、诊断过程和修改历史不得进入普通终稿。

## 7. 模块接口

每个模块文件必须声明：

```yaml
module_id: AW-01
name: strawman-guard
version: 1.0
default_enabled: true

stages:
  - prepare
  - audit
  - validate

reads:
  - intent_spec
  - source_material
  - draft

writes:
  - diagnostics
  - patch_proposals
  - validation_results

invariants:
  - preserve_user_position
  - do_not_invent_evidence

revalidate_after:
  - any_semantic_patch
```

所有模块还必须满足：

- 只写自己负责的诊断字段；
- 不直接覆盖其他模块状态；
- 不自行反复重写全文；
- 不把内部控制信息输出到终稿；
- 不为修复本模块问题而制造另一类问题；
- 不扩大用户授予的调查或工具权限；
- 不把未执行或失败的复验标为通过。

## 8. 模块注册表

1.0 在 `SKILL.md` 中注册：

| ID | 模块 | 文件 | 阶段 | 默认 | 依赖 |
|---|---|---|---|---|---|
| AW-01 | 稻草人保护 | `references/modules/01-strawman.md` | prepare、audit、validate | 启用 | 无 |
| AW-02 | 逻辑断裂控制 | `references/modules/02-logic-break.md` | plan、compose、audit、validate | 启用 | AW-01 形成的论点定义 |
| AW-03 | 防御性写作控制 | `references/modules/03-defensive-writing.md` | prepare、compose、audit、resolve | 启用 | 共享证据边界 |

04—10 在规则成熟并完成测试前不注册、不进入正式运行流程，也不创建空白运行模块。

新增模块必须：

1. 遵守模块接口；
2. 声明阶段、输入、输出、不变量和复验条件；
3. 提供独立测试；
4. 提供至少一个集成回归案例；
5. 更新注册表后才正式启用。

## 9. 冲突处理

多个模块提出冲突修改时，按以下优先级裁决：

1. 用户明确要求与核心论点不得被擅自替换；
2. 不得捏造事实、证据、来源或确定性；
3. 修订前后的真实含义必须保持；
4. 关键逻辑关系和必要条件必须完整；
5. 再优化防御表达和其他写作问题。

具体规则：

- AW-02 要求限定、AW-01 判断论点会被削弱时，保留用户论点，将限定作用于模型新增依据或适用条件；
- AW-03 要删除防御句、AW-02 判断其包含必要逻辑时，抽取有效信息并改为肯定式表达；
- AW-01 保护的强观点缺少材料时，将其保留为作者判断，不为其补造事实；
- 多模块修改同一范围时，合并为一个补丁后执行。

## 10. 输出契约

默认只输出可直接使用的成稿，不展示内部双向推演、论证地图、模块诊断或修复历史。

只有存在需要用户决定的证据缺口时，输出：

```text
【完整稿】
可直接使用的正文

【待确认的模糊陈述】
U01｜精确范围与完整句
缺少：对象、场景、指标、基线、数据或来源
当前不能安全具体化的原因：……
可选：网络调查搜集材料 / 我来补充 / 仅保留当前叙述 / 删除当前叙述
```

四个用户可见选项分别映射到内部状态 `INVESTIGATE`、`PROVIDE`、`KEEP`、`REMOVE`。内部状态码不替代中文选项进入交付内容。

未经逐项授权不得调查。用户只授权一个项目时，权限不得扩展到其他项目。

## 11. 测试与发布门槛

### 11.1 模块验证

分别运行 AW-01、AW-02、AW-03 的已有测试，保留基线、加载规则后的输出、人工判断和已知边界。

### 11.2 集成验证

至少覆盖：

- AW-03 删除内容后没有产生逻辑断裂；
- AW-02 添加限定后没有改变用户立场；
- AW-01 保护强观点时没有诱发证据编造；
- 待确认清单只在存在可行动证据缺口时出现；
- 三个模块同时运行时没有内部标签泄漏。

### 11.3 触发验证

覆盖自动触发、显式调用、关闭整个 Skill、关闭单个模块和不应自动触发的任务。

### 11.4 包验证

使用 Skill Creator 提供的 `quick_validate.py` 检查目录名、frontmatter、引用路径和未完成脚手架。格式通过不等于行为验证通过。

### 11.5 发布说明

发布结果必须分别列出已通过、已知限制和尚未覆盖的项目。不能把候选规则存在或单次样本通过表述成问题已经彻底解决。

## 12. 版本策略

- `1.0.x`：修正规则漏洞、调整措辞和补充测试，不改变公共接口；
- `1.x`：增加可选模块或向后兼容的诊断字段；
- `2.0`：修改共享契约、阶段语义或模块接入方式。

1.0 稳定接口包括：阶段名称、共享状态核心字段、诊断与补丁接口、用户开关方式、正文与待确认项边界。

模块内部规则可以在遵守稳定接口和测试要求的前提下继续演进。
