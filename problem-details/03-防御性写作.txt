
# 防御性写作

状态：候选规则 V2；前三类机制已完成首轮测试，第四检查器已按既有失败修订，等待用户测试。

## 1. 定义与目标

防御性写作是指：文本主动引入一个不需要进入正文的对立对象、排除项、潜在质疑或极端解释，并围绕它进行反驳、澄清、限定或免责声明，导致正文偏离用户真正要表达的内容。

不必要的防御对象主要有两个来源：

1. 模型根据常见讨论自行补出一个用户和材料都没有提出的对手；
2. 用户为了纠正生成结果而说“不要 A，要 B”，模型却把 A 以及围绕 A 产生的解释继续带入修改稿。

本模块负责生成前预防、生成中控制、生成后审计、防御链剪枝、局部修复、语义复验，以及对未解决模糊限定的逐项确认。它不负责空泛句首或空洞段落开头的检测；相关问题暂留给“废话”模块处理。

**核心原则**：优先直接陈述用户真正要表达的内容。只有任务要求、真实争议、证据边界或重大误导风险需要时，才引入反驳、限定和免责声明。不能为减少“AI味”牺牲准确性。

典型失败：

```text
用户要求：不要把它写成普通聊天机器人，要突出它能规划并执行任务。
失败正文：它不是普通聊天机器人，而是能够规划并执行任务的智能体。
目标正文：它能够根据目标规划步骤、调用工具，并结合执行结果调整行动。
```

## 2. 问题分类与边界

| ID | 类型 | 定义 | 示例 |
|---|---|---|---|
| DW01 | Unsolicited Opposition | 用户和材料没有提出某观点，模型自行构造该观点再反驳 | “这并不是要取代教师，而是……” |
| DW02 | Constraint Leakage | 用户以“不要 A，要 B”约束生成，模型却在正文重述或反驳 A | “它不是普通聊天机器人，而是……” |
| DW03 | Overqualification | 为预防质疑而叠加限定、弱化词或人为缩小范围 | “可能在一定程度上也许……” |
| DW04 | Preemptive Disclaimer | 主动防御尚未出现的质疑、极端解读或例外 | “这并不意味着所有人都……” |
| DW07 | Unresolved Vagueness | 模糊限定掩盖了缺失的对象、条件、场景、指标或证据 | “AI可能在一定程度上提高效率” |

DW05 `Empty Lead-in` 与 DW06 `Empty Paragraph Opening` 按当前范围决定暂不在本文件实施，编号保留用于与原交接方案和测试记录对应。

### 2.1 非目标

- 不禁用“不是……而是……”“并不意味着”等句式；
- 不把出现否定词直接判定为防御性写作；
- 不要求文章回避所有反方观点；
- 不把所有“可能”改成确定语气；
- 不自动补充未经证实的数据、群体、场景或研究结论；
- 不因追求直接而删除必要条件、安全提示或证据边界；
- 不在未获授权时进行外部调查。

### 2.2 必须保留的情况

- 用户明确要求反驳、比较、辩论或回应异议；
- 材料中存在真实争议或需要纠正的错误；
- 概念区分是理解核心论点不可缺少的条件；
- 不加限定会超出证据能够支持的范围；
- 安全、医疗、法律等高风险内容需要风险说明；
- 否定结构具有独立、不可替代的信息贡献。

保留时记录具体理由，不能用“更加严谨”作为空泛理由。

## 3. 与其他问题的边界

- 防御内容歪曲了用户原论点时，本模块判断该防御是否必要，`01-稻草人`检查立场是否被加强、削弱或替换。
- 删除防御内容后出现推论缺口时，使用`02-逻辑断裂`复验关系与推进。
- “不是 A 而是 B”只是机械重复的文体结构、并未回应防御对象时，属于文体过度对称。
- 限定词的强度与依据失衡、但并非为了防御质疑时，属于过度使用级别修饰。
- 空泛引导语和空洞段首暂由废话模块处理，不在本模块检查。
- 同一句可以触发多个模块；本模块只决定对立对象、排除项和防御链是否有必要进入正文。

## 4. 总体流程

```text
用户论点 + 修改要求 + 可用材料 + 来源权限
        ↓
[Preflight] Intent & Constraint Parser
        ↓
[Preflight] Assertion-First Planner + Evidence Boundary Mapper
        ↓
[Compose] Paragraph Draft → Trigger Detector → Defensive Necessity Gate
        ↓                          ↓
        └──── KEEP / DIRECT / CALIBRATE / DROP / REVIEW
        ↓
完整草稿
        ↓
[Post] Defensive Pattern Audit + Cascade Pruning
        ↓
Unified Rewrite Engine
        ↓
Semantic Consistency Validator → 完整可读稿
        ↓
[Post] Audit 4: Uncertainty Resolver（只检测，不自动调查）
        ↓
若存在可行动项：完整稿 + 精确问题范围 + 逐项选项
        ↓
用户逐项决定：网络调查搜集材料 / 我来补充 / 仅保留当前叙述 / 删除当前叙述
        ↓
仅对已授权项调查或修改 → 局部复验 → 最终稿
```

第四检查器不阻塞成稿。必须先完成防御性审计、统一修复和语义复验，形成完整可读稿；然后才能列出需要用户决定的模糊陈述。未经授权不得调查或擅自具体化。

在无法拦截 token 生成的环境中，以段落级“生成—检查—修复”模拟生成中控制，不宣称实时 token 级控制。

## 5. 生成前：意图与约束分流

### 5.1 输入拆分

将输入拆分为：

- `content_objectives`：正文必须回答或表达的目标；
- `user_position`：需要忠实发展的用户核心立场；
- `exclusion_constraints`：只用于排除生成方向的 A；
- `required_oppositions`：用户明确要求正文讨论或反驳的 A；
- `contextual_disputes`：材料和上下文中真实存在的争议；
- `evidence_boundaries`：证据能够支持的对象、范围、条件与强度；
- `style_and_genre`：分析、评论、说明、辩论、叙事等；
- `allowed_sources`：用户材料、已有上下文、允许检索的来源范围。

### 5.2 排除项不等于反驳义务

```text
exclusion_constraints ≠ required_oppositions
```

用户说“不要 A，要 B”，默认含义是用 A 约束内部生成，只在正文中完成 B。不得仅因为 A 出现在用户提示里，就认为读者也需要看到 A。

只有用户明确要求解释为什么不是 A、比较 A 与 B、反驳 A，或者不排除 A 会造成重大误解时，A 才能进入 `required_oppositions`。

### 5.3 正向陈述草案

对每个核心目标先形成 `direct_assertion`：

> 如果完全不提 A，怎样直接、完整并且证据匹配地表达 B？

先写正向陈述，再判断是否存在确切的反驳义务、概念歧义或证据边界。不得为了显得完整、严谨或平衡而凭空生成对手。

### 5.4 限定强度校准

- 基础事实直接陈述；
- 有适用范围时明确对象、条件或场景；
- 证据不确定时保留必要概率；
- 证据不足时不捏造确定性；
- 避免把“可能、一定程度上、部分情况下、也许”等同义弱化叠加使用；
- 限定不能代替缺失的证据、指标和论证对象。

### 5.5 内部输出契约

```json
{
  "content_objectives": ["说明AI Agent的自主规划能力"],
  "user_position": "AI Agent能够围绕目标规划和执行任务",
  "exclusion_constraints": ["不要写成普通聊天机器人"],
  "required_oppositions": [],
  "contextual_disputes": [],
  "evidence_boundaries": ["不能夸大自主性和工具权限"],
  "genre": "analysis",
  "direct_assertions": ["AI Agent能够根据目标规划步骤、调用工具，并结合结果调整行动。"],
  "allowed_sources": "user_context_only"
}
```

这些字段是内部构思状态，不得进入终稿。

## 6. 生成中：Defensive Necessity Gate

### 6.1 触发器只负责召回

候选触发形式包括：

- 对立式：“不是……而是……”“并非……而是……”；
- 防御澄清：“这并不意味着……”“不能简单理解为……”；
- 免责声明：“没有证据表明不能……”“这不代表所有……”；
- 假想对手：“有人可能认为……”“一种常见误解是……”；
- 模糊限定：“在一定程度上可能……”“也许”“不完全排除……”；
- 没有固定触发词，但语义上反驳了未出现的观点。

触发器命中只产生 `candidate`，不得按关键词直接删除或改写。

### 6.2 对象溯源

对每个候选项记录：

```text
defended_against
source
```

`source` 可取：

```text
user_required
contextual_dispute
user_exclusion_constraint
evidence_boundary
model_introduced
unknown
```

### 6.3 必要性判断

逐项检查：

1. `task_necessity`：用户是否要求正文回应该对象？
2. `evidence_necessity`：不限定是否会超出现有证据？
3. `context_necessity`：上下文是否存在真实且重要的歧义或争议？
4. `information_necessity`：该句是否提供不可替代的信息？
5. `risk_necessity`：删除后是否会造成安全、法律、医疗或其他重大误导风险？

安全和事实准确性可以单独构成保留理由；不做机械投票，也不使用未经验证的加权总分。

### 6.4 决策动作

- `KEEP`：对象真实、回应必要且表述准确，保留并记录理由；
- `DIRECT`：删除不必要的反面铺垫，直接陈述 B；
- `CALIBRATE`：保留证据需要的不确定性，删除重复弱化和防御框架；
- `DROP`：没有独立贡献的反驳、免责声明或铺垫，删除；
- `REVIEW`：来源、证据或修改风险不明，进入成稿复核。

`REVIEW` 不自动等于询问用户。只有歧义会实质改变用户立场、文章方向或关键结论时，才在成稿前提出一个最关键的问题；局部问题采用保守解释或留给第四检查器。

### 6.5 防御链剪枝

追踪一个不必要对象 A 衍生出的反驳、例外、澄清和免责声明：

```text
A → Q1（反驳A）→ Q2（防止反驳过头）→ Q3（补充A的例外）
```

A 被移除后：

1. 逐项重审 Q1、Q2、Q3；
2. 没有独立贡献的依赖项一并删除；
3. 含有独立事实的内容脱离 A，改成正向陈述；
4. 不做整链盲删；
5. 检查 B 是否重新成为段落中心；
6. 检查剪枝后是否产生逻辑断裂。

## 7. 生成后：防御审计与统一修复

### 7.1 Defensive Pattern Audit

全文重新定位 DW01—DW04，记录：

```text
span
defended_against
source
necessity
reason
proposed_action
context
```

执行删除测试：删除或正向改写后，核心事实、用户要求、证据强度、必要条件与误导风险是否仍然保持？

- 如果全部保持，优先最小删除或 `DIRECT`；
- 如果丢失必要信息，选择 `CALIBRATE`、正向改写或保留；
- 不以语言是否流畅代替必要性判断；
- 不因句式命中就判定问题。

### 7.2 Constraint Leakage Audit

将用户修改要求与实际正文对照：

- 用户要求删除的 A 是否仍以否定形式出现？
- 正文是否复述了纠错过程？
- 是否存在“虽然不是 A”“不能理解为 A”等残留？
- A 是否继续产生例外、澄清或免责声明？
- 是否把用户的内部约束误写成面向读者的论证？

### 7.3 Cascade Pruning Audit

- 删除 A 后是否仍有失去指代对象的句子？
- 附属澄清是否具有独立事实贡献？
- 防御内容是否挤占了 B 的论证位置？
- 修复是否又引入新的假想对手？

### 7.4 Unified Rewrite Engine

各检查只生成 `diagnostics` 与 `patch_proposals`，不得各自直接反复改写全文。统一修复器合并重叠范围并选择最小必要改动。

修复优先级：

```text
删除无贡献内容
→ 直接陈述正面内容
→ 合并必要限定
→ 重构局部句段
→ 保留确有必要的反驳
```

不得新增事实、数据或想象中的反方观点；不得为了衔接重新添加已经删除的防御铺垫。

### 7.5 Semantic Consistency Validator

在第四检查器前比较修复前后的文本：

- 用户核心立场和内容目标未被改变；
- 没有新增未获支持的事实；
- 不确定性未被无依据提升为确定性；
- 必要范围、条件和风险提示仍然保留；
- 防御链剪枝没有破坏论证关系和段落衔接；
- 修复没有引入新的防御性写作；
- 排除约束没有重新泄漏。

验证失败时回滚对应 patch 或标记人工复核。此时必须先形成一份完整、可独立阅读、可向用户展示的稿件。

## 8. Audit 4：Uncertainty Resolver

### 8.1 识别阶段：只检测，不自动调查

第四检查器不以“可能”“一定程度上”等模糊词作为必要触发条件，而以“正文结论所需的信息是否缺失”为判断基础。

在已经完成前三类修复并通过语义复验的稿件中，逐项对照正文主张与可用材料，识别缺乏具体对象、条件、场景、指标、基线、数据或来源的经验性效果主张。经验性效果包括效率、准确率、成本、质量、满意度、转化率、风险降低，以及其他需要观察或测量才能成立的实际结果。

以下形式都属于检查范围：

```text
可能提高效率
在一定程度上改善体验
部分情况下具有积极作用
也许能够带来更好的结果
减少人工判断并改善工单流转效率，但目前缺少测试数据
```

最后一种形式虽然没有使用模糊限定词，仍然存在证据缺口。前句的效果断言与后句的证据免责声明必须合并检查，不能按单句分别放行。

不是所有模糊词都需要上报。以下情况直接保留：

- 有明确证据支持的概率表达；
- 对随机性、风险或未来结果的必要表述；
- 已经说明对象、条件和判断范围；
- 进一步具体化不会改变读者理解，也不需要额外证据。

### 8.2 可自动处理与必须确认的边界

优先使用已有上下文安全具体化，但不得补造外部事实。

先区分三类内容：

- `function_fact`：材料直接给出的功能或已经发生的行为；
- `expected_mechanism_or_design_value`：根据功能可以说明的工作方式、预期机制或验证价值；
- `observed_effect`：声称效率、准确率、成本、质量、满意度等实际结果已经发生变化。

功能事实可以直接写。预期机制必须写成机制、目的或待验证价值，不能伪装成已经实现的效果。实际效果必须由相应材料支持；没有支持时，即使正文已经承认“缺少数据”“尚不能判断改善了多少”，也不能视为缺口已解决。

- 已有材料明确对象、场景或维度：可以补全；
- 通过逻辑即可缩小范围：可以收窄；
- 重复弱化但仍有必要不确定性：合并限定；
- 语句无论如何都不推进内容：可以建议删除；
- 需要新数据、外部事实或用户业务背景：必须进入用户确认；
- 具体化会实质改变用户核心立场：不得自动处理。

对“经验性效果主张 + 证据免责声明”的组合，必须执行以下处理：

1. 在完整稿中把材料能够支持的部分改写为功能事实、预期机制或验证目标；
2. 不得先把实际效果写成事实，再用免责声明回撤；
3. 将仍需数据判断的实际效果转换为独立待确认项；
4. 免责声明只能说明缺口，不能替代待确认项，也不能关闭第四检查器。

只有满足以下任一条件，相关项目才可以不进入待确认清单：

- 可用材料已经支持该实际效果；
- 完整稿中已经删除该实际效果主张，并且不再暗示它已经发生；
- 用户已经对该项目选择“仅保留当前叙述”“删除当前叙述”，或明确关闭待确认清单。

### 8.3 待确认项的数据要求

每个需要用户决定的项目必须包含：

- `item_id`；
- 精确 `span`；
- 所在段落和字符偏移；
- 完整句及足够上下文；
- 具体缺少什么；
- `missing_fields`，例如受益对象、任务场景、改善维度、数据、来源；
- 推荐调查问题或需要用户提供的信息；
- 为什么当前不能安全具体化。

展示顺序必须是：

1. 完整的已修订稿；
2. 单独列出的“待确认模糊陈述”；
3. 每项独立的处理选项。

没有待确认项时直接交付完整稿，不制造额外交互。

“只输出正文”“不要解释过程”等通常输出要求，只排除内部规划、审计过程和元话语，不自动关闭第四检查器。只要存在需要新证据、用户背景或外部调查才能安全具体化的可行动项，输出必须采用以下正向契约：

```text
【完整稿】
可直接使用的完整正文

【待确认的模糊陈述】
U01｜精确原文范围与完整句
缺少：对象、场景、指标、数据或来源
当前不能安全具体化的原因：……
可选：网络调查搜集材料 / 我来补充 / 仅保留当前叙述 / 删除当前叙述
```

该清单位于正文之后，不属于正文，也不展示内部推理。只有用户明确要求关闭待确认清单、接受现有模糊程度或已经对该项选择“仅保留当前叙述”时，才不展示相应项目。

### 8.4 用户逐项决定

每项独立提供以下四种面向用户的选择；英文状态码只用于内部记录，不得替代中文选项进入交付内容：

- **网络调查搜集材料**（内部状态 `INVESTIGATE`）：用户授权 AI 只针对该项调查核实；
- **我来补充**（内部状态 `PROVIDE`）：用户补充数据或背景；
- **仅保留当前叙述**（内部状态 `KEEP`）：保留现有表达，不再追问；
- **删除当前叙述**（内部状态 `REMOVE`）：删除该陈述，并检查上下文和论证完整性。

允许用户只处理部分项目。某一项的授权不得扩展到其他项目。用户未回应时，完整稿仍可交付，待确认项保持 `PENDING_USER_DECISION`，不得伪称已经调查或解决。

### 8.5 授权后的具体化

信息来源优先级：

```text
已有上下文
→ 可证成的逻辑推断（不得写成外部事实）
→ 用户授权的外部事实调查
→ 用户补充材料
```

调查结果必须能追溯到具体来源，并检查来源时间、适用群体、指标定义和研究局限。检索不可用、证据冲突或不足时如实报告，不虚构数据，也不强行删除必要限定。

每项修改后只复验受影响句、相邻段落和相关论证链；必要时进行全文轻量复查。保留用户批准前的版本，支持回滚。

### 8.6 交互状态机

```text
DETECTED → PRESENTED → (INVESTIGATE | PROVIDE | KEEP | REMOVE)
```

- `INVESTIGATE → RESEARCHING → (RESOLVED | INSUFFICIENT_EVIDENCE | RESEARCH_UNAVAILABLE)`；
- `PROVIDE → WAITING_USER_DATA → RESOLVED`；
- `KEEP → CLOSED_UNCHANGED`；
- `REMOVE → REMOVED_AND_VALIDATED`。

`INSUFFICIENT_EVIDENCE` 与 `RESEARCH_UNAVAILABLE` 不得自动升级成确定性结论；可以再次让用户选择保留、删除或提供资料。

## 9. 内部状态与终稿边界

以下内容只用于内部规划、审计和交互，不得混入普通终稿：

- A/B、`content_target`、`user_position` 等内部标签；
- `exclusion_constraints` 与用户纠错历史；
- 防御对象来源和必要性记录；
- KEEP、DIRECT、CALIBRATE、DROP、REVIEW；
- 防御链关系和 patch log；
- 审计器名称、完成状态与自评分。

只有第四检查器发现确实需要用户决定的项目时，才在完整正文之后展示结构化待确认清单。该清单不是正文的一部分。

## 12. 各阶段职责与防越权约束

**Planner**：解析内容目标、用户立场、排除项、真实反驳义务和证据边界；先形成直接陈述，不为增强论证感自行制造对手。

**Composer / Gate**：发现否定、免责声明或模糊限定时，标明所防御对象及来源；只有存在必要性时才保留；追踪防御链依赖。

**Defensive Auditor**：输出精确问题范围、对象来源、必要性和建议动作，不直接反复修改全文。

**Rewriter**：统一合并诊断并执行最小修复；禁止新增事实、数据或想象中的反方观点。

**Validator**：比较修复前后的立场、事实、证据强度、用户约束和必要限定；不能用“更流畅”代替语义一致性。

**Uncertainty Auditor**：只识别真正缺少具体依据的表达，生成待确认清单；不得先调查再征求同意，也不得先删除问题句来规避用户确认。

上述职责可以由同一运行环境分阶段完成。如果环境支持独立调用，Validator 应只读取原始任务和实际正文，重新判断；否则只能称为同会话复核，不能宣称完全独立验证。

## 13. 测试矩阵

T07—T10 对应原方案中的空泛句首和段落开头测试，按当前决定暂不纳入本模块；编号保留，避免与原交接方案失去对应。

| ID | 输入或场景 | 预期 |
|---|---|---|
| T01 | 番茄炒蛋、五花肉与连续免责声明 | 直接陈述常见做法，剪除无关防御链 |
| T02 | 用户“不要 A，要 B” | 正文表达 B，不自动重复“不是 A” |
| T03 | 用户明确要求反驳 A | 保留必要反驳 |
| T04 | 真实争议或辟谣场景 | 保留证据充分的澄清 |
| T05 | “这并不意味着……”但无真实歧义 | 删除或正向改写 |
| T06 | “可能在一定程度上也许……” | 校准冗余词，不擅自提高确定性 |
| T11 | 模糊效果没有场景、对象和指标 | 先成稿，再展示精确范围和逐项选项 |
| T12 | 两个待确认项，只授权第一个调查 | 只调查第一个，第二个保持待确认 |
| T13 | 用户选择“仅保留当前叙述” | 保留原文，不反复追问 |
| T14 | 用户选择“我来补充”但尚未提供资料 | 标记等待用户，不臆造内容 |
| T15 | 用户选择“删除当前叙述” | 删除并检查段落逻辑 |
| T16 | 调查工具不可用或证据不足 | 明示无法核实，保留必要不确定性 |
| T17 | 医学证据只说明“不证明对所有人有效” | 不改写成“对部分人有效” |
| T18 | 多项修改范围重叠 | 单次合并 patch，不重复引入防御铺垫 |
| T19 | 没有待确认模糊表达 | 直接交付完整稿，不制造交互 |
| T20 | 中文和 emoji 的偏移定位 | span 与稿件版本绑定且定位准确 |
| T21 | 反驳 A 的附属澄清含独立事实 | 删除无必要 A，保留并正向表达独立事实 |
| T22 | 修复后意外引入“并不意味着” | Validator 检出并回滚或修复 |
| T23 | 常见争议话题但用户未要求回应 | 不因常见争论自动生成对手 |
| T24 | 用户连续纠正两次 | 最终稿不复述修改历史和被排除内容 |
| T25 | 否定结构承担必要概念定义 | 不按关键词误删 |

测试必须记录原始输入、无规则输出、加载规则后的输出、问题跨度、对象来源、必要性判断、修复动作、误删、漏报、事实强度漂移和用户确认状态。不能只计算否定词数量，也不能只凭模型对自身输出的评分宣称有效。

## 14. 基线观察

当前无规则基线已观察到：

1. 用户要求“不要写成普通聊天机器人”，模型仍生成“它不是只会问答的聊天机器人，而是……”，构成明确的约束泄漏；
2. 修辞命题中的否定结构可能承担必要概念界定，不能机械删除；
3. 用户明确要求反驳时，模型能够保留真实对立对象，这是需要保护的正例；
4. 材料缺少数据时，模型可能先写“有助于提升效率”，再用免责声明回撤，却不把缺口转成第四检查器的逐项决定。

完整基线记录位于 `evals/defensive-writing/baseline-review.md`。

## 15. 验收标准

1. 同时处理模型自造反方与用户排除项泄漏；
2. 能区分触发词与真正问题，不禁用否定句；
3. `exclusion_constraints` 不自动转为 `required_oppositions`；
4. 能在生成中执行来源追溯和必要性判断；
5. 能剪除完整防御链，同时保留具有独立贡献的事实；
6. 统一修复不会改变用户立场、事实或证据强度；
7. 必要反驳、定义区分、高风险提示和真实不确定性得到保留；
8. 第四检查器只在完整稿形成并复验后运行；
9. 第四检查器能把模糊陈述转换为精确、可行动的待确认项目；
10. 每个项目独立提供“网络调查搜集材料、我来补充、仅保留当前叙述、删除当前叙述”四个用户可见选项，并在内部映射为 INVESTIGATE、PROVIDE、KEEP、REMOVE；
11. 未授权项目不得调查或擅自具体化；
12. 无证据不得填充数字、对象、场景或来源；
13. 所有修改保留 patch log、稿件版本和回滚能力；
14. 覆盖相关测试矩阵，并记录误报、漏报、约束泄漏率、必要限定保留率和语义漂移；
15. 内部控制标签和修改历史不进入普通终稿。

## 16. 建议实施顺序

**M1**：意图数据结构、两类防御对象来源、基础触发与溯源；

**M2**：Defensive Necessity Gate、段落级工作流和防御链剪枝；

**M3**：生成后防御审计、约束泄漏审计、统一修复和语义复验；

**M4**：完整保留第四检查器、完整稿展示、逐项授权状态机，以及按授权调查或补充；

**M5**：测试矩阵、误报分析、回归评测、接口文档和典型样例。

## 17. 当前完成边界

本文件目前是候选规则，不是已经验证有效的发布版本。首轮测试中，约束泄漏、防御链剪枝与必要反驳保护符合预期；第四检查器则出现失败：模型使用“效果断言 + 证据免责声明”避开了以模糊限定词为主的识别条件。V2 已改为按结论所需证据是否缺失触发，并明确区分功能事实、预期机制与实际效果，等待用户测试。完整测试矩阵与人工盲审完成前，不能宣称防御性写作问题已经解决。

**最终原则**：直接表达优先；必要反驳与限定保留；排除项不泄漏；模糊缺口必须可定位；调查逐项授权；先成稿再确认；绝不以消除防御性表达为由编造事实。
